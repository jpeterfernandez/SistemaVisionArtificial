ACTUALIZACION DE ALCANCE - FASE ACTUAL
El usuario pidió pausar en esta fase las tareas de integración, latencia y conectividad relacionadas con Odoo. No se amplían en esta fase; el código de Odoo y métricas que ya estaba en la copia se conserva. El foco actual es operación interna: permisos por zona y acción, control de usuarios, consulta/exportación de registros y auditoría.

Implementado en esta fase:
- Roles ADMIN/OPERATOR/VIEWER con asignación de zonas por usuario; ADMIN tiene alcance global y los otros roles requieren una o más zonas.
- Las órdenes nuevas pertenecen a una zona; órdenes, cámaras, eventos, detecciones, tendencias y dashboard se filtran/validan por alcance.
- La zona se guarda como snapshot en eventos y detecciones. Cambiar la zona de una cámara no reclasifica su historial.
- Asociaciones entre eventos y órdenes de zonas diferentes se rechazan. Confirmar una unidad terminada sigue siendo una acción OPERATOR/ADMIN.
- La interfaz de usuarios permite administrar zonas; producción muestra la zona y solo presenta acciones compatibles con el rol.
- Eventos, órdenes, detecciones y auditoría tienen exportación CSV. Los archivos aplican el mismo alcance de acceso que las consultas.
- Hay auditoría de cambios administrativos y una vista de historial; los detalles no incluyen passwords, claves Odoo ni fuentes de cámara.
- Se añadieron migraciones para auditoría, alcance de usuario/orden y snapshot de zona en registros históricos.

Pendiente fuera de esta fase:
- No se añadió trabajo nuevo de Odoo ni métricas de latencia/conectividad. La integración existente se mantiene sin ampliaciones.
- La semántica de etapa final usa VINILADO como configuración por defecto. Si el flujo de planta difiere, cambiar FINAL_PRODUCTION_STAGE antes de usar el conteo.
- Respaldos/restauración requieren que operación ejecute y valide periódicamente los scripts documentados; no se configura un scheduler de respaldo en esta fase.

2. Hallazgos adicionales prioritarios

P0 - Integridad de sincronizacion Odoo
En la copia revisada, sync_pending_events_to_odoo() cambia sync_status a SINCRONIZADO sin ejecutar una escritura remota. OdooClient solo consulta ordenes y prueba la conexion. Una cola con reintentos no basta si no existe una operacion remota confirmable.
Recomendacion: definir el destino y contrato de eventos en Odoo; enviar un identificador externo estable por evento; comprobar primero si ya fue recibido; marcar SINCRONIZADO solo despues de una confirmacion remota. Si la respuesta es incierta, conservar el evento para reintento idempotente.
Criterio: una prueba con un Odoo simulado verifica envio, deduplicacion, error recuperable, reintento y que ningun fallo termine en SINCRONIZADO.

P0 - Secretos y credenciales de produccion
La configuracion tiene una clave JWT y credenciales de base de datos predeterminadas. El script de administracion permite crear el usuario admin con la contrasena admin123 si no se reemplaza. La clave API de Odoo se guarda como texto en la tabla de configuracion.
Recomendacion: fallar al iniciar en produccion si siguen valores de desarrollo; quitar contrasenas predeterminadas; usar secretos del entorno o un gestor de secretos y restringir el acceso a respaldos. Rotar las credenciales ya usadas en entornos accesibles.
Criterio: una configuracion de produccion con secretos por defecto no inicia y ningun secreto aparece en respuestas, logs o exportaciones.

P1 - Proteccion de credenciales de camaras
La respuesta Camera incluye el campo source para cualquier usuario autenticado. Una URL RTSP puede contener usuario y contrasena y la interfaz la muestra. Esto expone credenciales a operadores/viewers y potencialmente a logs del navegador.
Recomendacion: separar la configuracion sensible de la fuente publica; devolverla solo a administradores o enmascarada; evitar mostrar credenciales y rotarlas si ya fueron compartidas.
Criterio: respuestas de lectura para roles no administradores no contienen usuario/contrasena ni URL de conexion reutilizable.

P1 - Sesiones del frontend
El JWT de sesion se guarda en localStorage, accesible a cualquier script ejecutado en el origen. El stream ya se cambio en esta revision para usar tickets de dos minutos ligados a la camara y al usuario, en vez del JWT de sesion en la URL.
Recomendacion adicional: evaluar cookies HttpOnly/Secure/SameSite con proteccion CSRF; si se conserva localStorage, reforzar CSP, dependencias y defensa XSS, y definir expiracion/renovacion de sesion.

P1 - Monitoreo real de camaras y recuperacion
La API actualiza estado al ejecutar la prueba manual de conexion; no hay una comprobacion periodica ni una politica de reconexion. El estado puede quedar obsoleto aunque el stream se haya perdido.
Recomendacion: servicio de salud con intervalos configurables, backoff, ultimo resultado y alerta persistente; coordinar las capturas para que la comprobacion no compita por una camara USB que esta transmitiendo. Mostrar estado, antiguedad del ultimo chequeo y accion de recuperar.
Criterio: desconectar una camara actualiza su estado dentro del intervalo acordado, genera una alerta y la reconexion no duplica streams.

P1 - Semantica de produccion y conteos
Asociar un evento actualiza la etapa y el estado de una orden, pero no se observa una regla de negocio que incremente produced_qty o cierre una orden. La definicion de conteo debe corresponder a eventos de fin de producto, no a cada deteccion de etapa.
Recomendacion: acordar la maquina de estados y las transiciones validas; derivar cantidades de eventos idempotentes y auditar correcciones manuales.
Criterio: eventos repetidos o reintentados no incrementan dos veces la cantidad, y solo un evento de finalizacion autorizado cierra una unidad/orden.

P1 - Disponibilidad y latencia en produccion
El health check informa el estado de la base, YOLO y Odoo, pero la condicion global depende principalmente de la base. El dashboard tambien prueba Odoo en la peticion, lo que puede sumar el timeout remoto a una consulta interactiva.
Recomendacion: separar liveness y readiness, medir latencia y errores por dependencia, evitar llamadas externas bloqueantes en cada consulta del dashboard y publicar metricas protegidas para alertas (API, base, YOLO, camaras, Odoo y cola).
Criterio: una caida de cada dependencia se refleja con claridad; el panel sigue respondiendo aunque Odoo este lento; se generan alertas con umbrales definidos.

P2 - Subida de imagenes y recursos
El endpoint lee el archivo completo en memoria antes de verificar el limite de 15 MB y confia en Content-Type para decidir si es imagen. El tipo puede falsificarse y muchas cargas simultaneas elevan memoria y CPU.
Recomendacion: lectura por bloques con limite, validacion real del formato y dimensiones maximas, limites de concurrencia y timeout de inferencia.
Criterio: archivos sobredimensionados, corruptos o con formato no admitido se rechazan antes de inferencia sin aumentar memoria de forma proporcional al tamano enviado.

P2 - Escalabilidad de inferencia
Las camaras y las inferencias de imagen comparten el mismo modelo y bloqueo de inferencia. Con varias camaras, la latencia puede crecer y el stream puede quedar limitado por el recurso compartido.
Recomendacion: medir latencia por camara y carga; establecer politica de prioridad/admission control; considerar un procesador central de frames recientes por camara. Si se ejecuta con varios workers, documentar que cada proceso podria cargar su propia copia del modelo.
Criterio: prueba con el numero esperado de camaras mantiene el FPS/latencia objetivo y el consumo de RAM/VRAM dentro del presupuesto.

P2 - Pruebas reproducibles
La prueba que exige tres camaras depende de datos presentes en la base configurada, y fallo en la ejecucion local. Esto hace que el resultado dependa del entorno y puede tocar datos ajenos a la prueba.
Recomendacion: usar una base aislada de test, sembrar fixtures dentro de la suite y limpiar/rollback entre pruebas. Agregar pruebas de roles, expiracion de tickets, idempotencia Odoo, filtros/paginacion y reconexion de camaras.
Criterio: pytest pasa desde una base vacia y no requiere haber ejecutado scripts manuales ni conectarse a servicios reales.

P3 - Auditoria y retencion
No se identifico una politica completa para auditar cambios de roles/configuracion ni para retener o depurar detecciones, eventos y metadatos de sincronizacion.
Recomendacion: registrar actor, accion, fecha y resultado para operaciones administrativas; definir retencion/archivado y respaldo con restauracion probada.
